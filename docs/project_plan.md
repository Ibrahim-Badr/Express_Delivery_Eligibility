# Project: Express Delivery Eligibility - Architecture and Migration Plan

This document describes the design, architecture and action plan to turn the experimental notebook into a robust Python application. It follows **Clean Code**, **SOLID** and **YAGNI**, using a simplified **Layered Architecture (Ports & Adapters)**. This is the first step of a larger project: the structure must make adding and modifying modules easy.

Decisions are recorded in `docs/adr/`:
- ADR 0001: local/in-memory adapters first
- ADR 0002: layered architecture and dependency rules
- ADR 0003: asynchronous prediction after `POST /v1/orders`

## 1. Repository and Environments
- **Repository name:** `eligibilite-livraison-express`
- **Environments:** dev, test, prod.
- **Configuration:** `pydantic-settings` loading typed variables from `.env.dev`, `.env.test`, `.env.prod`. Only `.env.example` is committed; real `.env.*` files are git-ignored.
- **Run in dev with a single worker** (in-memory state, see ADR 0001).

## 3. Dependency Rules (see ADR 0002)
1. `core` imports nothing from other layers.
2. `etl` imports only `core` and stays pure.
3. `ml` imports `core`, `etl`, `infra.abstractions`; never a concrete adapter, never `api`.
4. `api` imports `core`, `ml`, `infra.abstractions`; never a concrete adapter.
5. Adapters implement `infra.abstractions` and import only `core`.
6. Only `main.py`, `cli.py` and `core/dependencies.py` know concrete adapters.
7. `FEATURE_COLUMNS` and enums are defined once in `core/constants.py`.

## 4. Applied Principles
- **SRP:** one file per router, one port per responsibility.
- **DIP:** `api` and `ml` depend on abstractions; adapters are injected.
- **YAGNI:** local adapters first (ADR 0001); `BackgroundTasks` before a real queue (ADR 0003).
- **DRY:** one ETL for training and inference; one source of truth for features.

## 5. Notebook to Application Mapping
| Notebook part | Destination |
|---|---|
| Data generation | `src/ml/data_generation.py` via `cli.py generate-data` |
| Cleaning / feature engineering | `src/etl/` |
| Pipeline, training, evaluation, model card (cell 55) | `src/ml/`, output in `artifacts/` |
| Unit prediction (cell 34) | `src/api/routers/predictions.py` + `ml/predictor.py` |
| Batch prediction (cell 46) | `POST /v1/predictions/batch` |
| Hardcoded paths / constants | `src/core/config.py`, `src/core/constants.py` |

## 6. API Contract Alignment (`openapi.yml`)
| Session | Operations |
|---|---|
| 1 | `/health`, `/health/ready`, `POST /v1/orders`, `GET /v1/orders/{id}`, `POST /v1/predictions` |
| 3 | `GET /v1/model` |
| 5 | `POST /v1/predictions/batch`, `GET /v1/predictions/{id}` |
| 7 | `GET /metrics` |

Constraints:
- `OrderFeatures` rejects extra or missing fields (422).
- `/health` never depends on external components; `/health/ready` returns 503 if `ModelRepository.is_available()` is false.
- At the end of each session, compare FastAPI's `/openapi.json` with `openapi.yml`.

## 7. ML & ETL Strategy
- Shared pure ETL functions in `src/etl/`.
- Training via `cli.py train`; metrics saved to `model_card.json`; pipeline saved with joblib.
- MLflow tracking is a future adapter (ADR 0001), not part of the first iteration.

## 8. Action Plan
1. **Scaffold:** directories, `__init__.py`, `.gitignore`, `.env.*`, `.env.example`, `requirements.txt`, `pyproject.toml`.
2. **Core & ETL:** `config`, `logging`, `errors`, `constants`, then `etl/`.
3. **ML:** migrate the notebook into `src/ml/`; implement `FileModelRepository`.
4. **Ports & adapters:** write the ABCs and the `Memory*` adapters.
5. **API:** schemas, error handlers, routers `health`, `orders`, `predictions`; `dependencies.py`.
6. **Bootstrapping:** `main.py` and `cli.py`.
7. **Testing:** `conftest.py` with in-memory fixtures; tests mirroring `src/`; contract check against `openapi.yml`.
8. **Later:** `model`, batch/history, `metrics`; migrations triggered by ADRs.
