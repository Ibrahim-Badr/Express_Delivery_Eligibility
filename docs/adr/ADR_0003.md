# ADR 0003: Asynchronous Prediction after `POST /v1/orders`

**Date:** 2026-10-06
**Status:** Accepted

## Context
The API contract (`openapi.yml`) states that `POST /v1/orders` persists the order through the `OrderStore`, queues it for prediction and returns **202 Accepted** immediately; the prediction itself is asynchronous. `POST /v1/predictions` remains synchronous (200). The result is later readable via `GET /v1/predictions/{order_id}` (session 5).

## Decision
For the initial iterations, use FastAPI **`BackgroundTasks`**:
1. The router validates the payload (`OrderFeatures`), generates `order_id` if absent, saves via `OrderStore`, schedules a background task, and returns `202 {order_id, status: "accepted"}`.
2. The background task calls `ml.predictor` and stores the result in the `PredictionStore`.
3. If the model is unavailable, the failure is logged and the order stays without prediction; it is never lost.

The queue is hidden behind the application code, so it can be replaced without changing the endpoint contract.

## Consequences
### Positive
- No broker to deploy; fits the in-memory adapters of ADR 0001.
- Respects the 202 contract.

### Negative
- Tasks are lost on process restart and are not shared across workers.
- No retry or back-pressure.

## Future Migration Triggers
Introduce a real queue (Redis/RQ, Celery, or a cloud queue) behind a `PredictionQueue` port when: predictions must survive restarts, throughput exceeds a single process, or retries are required. Revisit together with ADR 0001 (database migration).
