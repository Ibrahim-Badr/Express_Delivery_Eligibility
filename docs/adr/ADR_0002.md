# ADR 0002: Layered Architecture with Ports & Adapters and Dependency Rules

**Date:** 2026-10-06
**Status:** Accepted

## Context
The project starts from an exploratory notebook and is only the first step of a larger objective: modules must be easy to add and modify later. An initial proposal grouped code by feature (vertical slicing: `orders/`, `predictions/`, `health/`, ...). For a project of this size it produced many near-empty folders.

## Decision
Use a simplified **layered architecture with ports & adapters** inside `src/`:

| Layer | Responsibility |
|---|---|
| `core/` | config (pydantic-settings), logging, domain errors, constants (`FEATURE_COLUMNS`, enums), dependency providers |
| `api/` | FastAPI routers (one file per responsibility), Pydantic schemas, error handlers |
| `etl/` | pure cleaning / feature functions shared by training and inference |
| `ml/` | data generation, pipeline, training, evaluation, predictor |
| `infra/` | `abstractions/` (ports) and adapters (`local/`, later `database/`, `mlflow/`, `prometheus/`) |

`src/main.py` and `src/cli.py` are the composition roots. Tests live in `tests/` (outside `src/`) and mirror it.

### Dependency rules (enforced by review, optionally by import-linter)
1. `core` imports nothing from the other layers.
2. `etl` imports only `core`, and stays pure (no I/O).
3. `ml` imports `core`, `etl`, `infra.abstractions`; never a concrete adapter.
4. `api` imports `core`, `ml`, `infra.abstractions`; never a concrete adapter.
5. Adapters in `infra/<tech>/` implement `infra.abstractions` and import only `core`.
6. Only `main.py`, `cli.py` and `core/dependencies.py` know concrete adapters.
7. `ml` never imports from `api` (HTTP schemas are not domain types).
8. `FEATURE_COLUMNS` and enums are defined once in `core/constants.py`; Pydantic schemas (`additionalProperties: false`) and ETL both import them.

## Consequences
### Positive
- Few, predictable folders; easy to explain and navigate.
- Add endpoint: new file in `api/routers/` + one `include_router` line.
- Swap technology: new adapter + one line in `dependencies.py` (or switch via `.env`).
- Training and inference share the same ETL, preventing training/serving skew.

### Negative
- A business capability spans several folders (e.g. predictions: router, predictor, port).
- If the project grows to many independent domains, regrouping by feature may become worthwhile; the dependency rules make that refactoring mechanical.
